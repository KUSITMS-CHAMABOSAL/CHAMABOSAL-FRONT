# 커밋·브랜치·이슈 규칙

## 커밋 메시지

형식: `{type}: {한국어 설명}`

| type       | 용도                                                       |
| ---------- | ---------------------------------------------------------- |
| `feat`     | 새로운 기능 추가                                           |
| `fix`      | 버그 수정                                                  |
| `chore`    | 설정, 빌드 스크립트, 패키지 의존성 관리                    |
| `docs`     | README, AI 규칙(`.claude/rules`, `CLAUDE.md`) 및 문서 변경 |
| `style`    | 코드 포맷팅 (동작 영향 없음)                               |
| `refactor` | 동작 변경 없는 구조 개선                                   |
| `ui`       | UI 작업 (화면·컴포넌트의 시각 작업)                        |

- 위 7개 외의 type은 쓰지 않습니다.
- 설명은 한국어로, 무엇을 했는지 짧게 씁니다. 예: `chore: 프로젝트 기본 설정`, `ui: 하단 탭바`

- 한 커밋에는 한 type의 변경만 담습니다. 기능 로직과 시각 작업이 섞이면 `feat`와 `ui`로 나눕니다.

## 이슈와 브랜치

- 이슈는 `.github/ISSUE_TEMPLATE/issue.yml` 템플릿으로 만듭니다.
  - 제목: `[Type] 작업 내용` (예: `[Feat] 앱 골격 구성`)
  - 브랜치 유형: 위 커밋 type과 같은 목록을 소문자로
  - 브랜치 작업 내용: 영문 kebab-case만 (예: `router-layout`). 한글이 들어가면 브랜치 자동 생성이 실패합니다.
- 이슈를 열면 워크플로가 `{type}/{이슈번호}-{작업내용}` 브랜치를 main에서 자동 생성합니다. 직접 브랜치를 만들지 않습니다.
- 이슈 1개 = 브랜치 1개 = PR 1개를 기본으로 합니다.

## PR

- `.github/PULL_REQUEST_TEMPLATE.md` 형식을 따르고, 연관 이슈를 `Closes #번호`로 연결합니다.
- 올리기 전에 `pnpm lint`와 `pnpm build`(앱인토스 빌드 포함)가 통과해야 합니다.
- UI 변경이 있으면 스크린샷을 첨부합니다.
